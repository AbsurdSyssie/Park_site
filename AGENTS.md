If you are helping someone from a GP practice set up or change their website, follow [skill/gp-practice-website/SKILL.md](skill/gp-practice-website/SKILL.md).

For the Park Medical Centre site-structure work, also use [practice/site-structure-review/REVIEW.md](practice/site-structure-review/REVIEW.md) as the approved implementation plan and route map. Keep existing public URLs, source content, the six primary navigation labels and order, and the CQC footer widget. The shared urgent-help panel is agreed for Home and Appointments only; keep the standalone Urgent help page and footer link. Give each non-home page its mapped semantic breadcrumb parent. The explicit project decisions in the review supersede older conflicting template guidance for this project.

Work in bounded, disjoint file scopes. Delegate implementation to Luna subagents and have Terra review the aggregated changes before committing or syncing; do not request routine reviews for small edits. Run deterministic audits first; use editorial judgement only where the tools cannot decide. Do not invent practice facts or describe clinical hazards as resolved. GP earnings and source/fact review remain pending; do not record practice sign-off. Do not publish or push unless asked.

Use WCAG 2.2 AA as the Park site accessibility baseline. Treat the selected WCAG 2.0 checks in earlier reviews as historical evidence. Record remaining manual and browser-based accessibility checks, and make conformance claims only when supported by a full assessment.

When writing patient-facing materials on the website, you must always make sure that it is intelligible to somebody with no knowledge of the internal workings of the website or the practice, and that the wording doesn't reference any work that you are currently doing but is universal and general in its scope. And also, language should be free of jargon at a reading level of age 10.
